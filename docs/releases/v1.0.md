# Clockchain v1.0

Released 2026-10-02 by the owner. Refs [#6](https://github.com/timepointai/clockchain/issues/6).

## What v1 is

v1 replaces single-signer v0 admission with the multi-signer rules in
[MULTI-SIGNER.md](../design/MULTI-SIGNER.md):

- **One admission path.** Every envelope, whether it arrives over HTTP, from an
  import, a restore or the publisher, passes the same `admit()`. There is no v0
  or raw-append ingress in v1 mode.
- **Authority.** A ledger Genesis creates a root grant. Grants delegate and revoke
  on the causal subject DAG, and revocation is scoped to the issuer's own grants.
  A bearer credential is transport only; a valid signature is not subject
  authority, and curators cannot override it.
- **Visible conflicts.** Corrections create new immutable revisions under a
  stable signed `subject_key`. Competing branches stay visible as contested until
  an explicit, signed Resolve by a surviving common grant. Asserted and receipt
  times never order authority.
- **Pinned edges and revision-scoped media.** Edges pin both endpoint revisions
  and bodies, and go stale when an endpoint changes. Media binds to a revision or
  event. A dispute never counts as support.
- **Governed rule identity.** `fold_version = (1, SHA256(fold manifest))`. The
  filter identity commits to the fold version, encoding, TT taxonomy hash,
  curator set, trust policy and `max_hops`. Every read names its `rule`,
  `corpus_digest` and view `commitment`; unknown fold versions are refused.
- **Runtime.** `cc-node` serves v1 when `CC_NODE_LEDGER=v1`, and fails closed if
  the stored identity differs from its configuration. `cc-publisher v1` signs a
  Genesis offline and submits it over HTTP. `ops/deploy-fly.sh --v1-fresh`
  accepts the exact image locally, then releases and checks it.

v1 starts on a fresh, empty database. There is no migration of v0 history; the
v0 database is kept as an archive.

## Governed defaults

The owner accepted every STAGE-E default as pinned for `fold_version` 1 on
2026-10-01, with production `max_hops = 4`. Each default changes only through a
new fold version. All but the restore rule (STAGE-E item 13, enforced in
`Store::restore_export`) are named fields of the fold manifest,
`crates/cc-core/src/v1/fold-manifest-v1.txt`. The full list with its rationale is in
[STAGE-E.md](../design/STAGE-E.md#owner-questions-governed-defaults-pinned-in-the-manifest).
In short:

- **Edges.** Relations are `causation`, `co_occurrence`, `disputes`, `influence`
  and `participation`. The dispute author is the source subject's creator. An
  endpoint with no current body makes the edge stale. Self-edges are admitted,
  and any valid basis may be reaffirmed.
- **Support.** Support uses every relation except `disputes`, over undirected
  adjacency, within `max_hops`. Every edge author and endpoint Genesis creator
  must be in the curator set. A same-subject query is unsupported.
- **Media.** Media targets a revision, subject event or edge event, and binds
  only to its creating event's revision. A missing revision leaves it pending,
  and nothing is inferred.
- **Subjects and time.** An authority-only fork contests the subject. `as_of`
  hides a later current revision without falling back, and an unknown asserted
  time is not visible.
- **Rows and restore.** Projection rows use the `cc.view-rows.json.v1` canonical
  schema, pinned by a conformance vector. Export and restore require the same
  filter identity.

## Launch

The release was an owner action. [HOLD.md](../../HOLD.md) allows deployment only
from the owner's workstation, never from CI or a cloud session, and
[FIRST-ENTRY.md](../FIRST-ENTRY.md) is its runbook.

The owner's launch record in HOLD.md (2026-10-02) states that:

- v1 was released onto the fresh database;
- the inaugural Engelbart 1968 Genesis was admitted on 2026-10-02 and is the
  only entry;
- production stays on private ingress, with posture `live`.

The owner's 2026-10-01 decisions in HOLD.md set the scope that release was
authorized for:

- a fresh, empty v1 database, with its rule identity bound to the owner's
  curator key set and production `max_hops = 4`;
- an inaugural entry with no media and no signed absence decision;
- the v0 database left untouched as an archive;
- the 1973 claim, its influence edge and both fixture images kept private and
  held.

The release evidence (acceptance, backups, health and receipts) is private.
[LAUNCH-EVIDENCE.md](../LAUNCH-EVIDENCE.md) gives the public mapping from each
#6 gate to merged PRs, named tests and the checks the release path runs.

## Legacy v0

These paths remain in the code and tests, but they are not part of the v1
service:

- legacy node mode (`cc-node` without `CC_NODE_LEDGER=v1`, and `cc-node migrate`);
- `cc-anchor-tick`;
- `cc-migrator`;
- the v0 `cc-publisher` commands;
- the v0 database archive.

Nothing was removed. See the [README](../../README.md#legacy-v0-paths).

## Known limits and follow-ups

The post-launch program is [STAGE-G.md](../design/STAGE-G.md). Its items that
change what v1 can do:

- **Update releases** (G1). `--v1-fresh` handles only an empty store. An update
  release for a bound, populated store, scheduled verified backups and
  monitoring are not built yet.
- **Delegated hot keys** (G2). `cc-publisher v1` builds only Genesis envelopes.
  The fold already admits Delegate and Revoke, but the publisher has no command
  for them, so the root curator key signs everything.
- **Content commands** (G3). There are no publisher commands yet for
  corrections, edges, attestations or reviewed multi-envelope entries.
- **Serving** (G4). Each snapshot recomputes the full fold. STAGE-E records the
  reaffirmation fixed point as O(L^2) and projection as O(edges x candidates).
  There is no snapshot cache and no read concurrency limit. The node signs no
  `NodeReceiptV1`; the type exists in `cc-core` but no route serves it.
- **Sealing** (G4). v1 runs no tick and has no external anchoring. External
  anchoring is a MULTI-SIGNER non-goal, and any sealing design is an owner
  question.
- **Public access** (G5, G6). There is no unauthenticated read gateway, explorer
  or in-browser verifier. Public exposure is an owner decision.
- **Consumers** (G7). Existing consumers were written against the legacy node
  API, which v1 mode does not mount. No typed v1 clients exist yet.

Generation and model calls remain held. Further entries, public exposure,
deploys, secrets and key ceremonies remain owner actions. Disposition of #6
remains the owner's decision.
